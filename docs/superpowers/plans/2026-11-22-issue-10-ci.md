# Issue #10 — CI en GitHub Actions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Que cada PR y cada push a `dev`/`main` valide, en un entorno limpio y sin secretos reales, la instalación reproducible, formato, lint, tipos, pruebas, build y la convención de commits del PR.

**Architecture:** Un workflow con dos jobs de nombre estable: `verificar` (instalación congelada + comprobaciones) y `commits` (solo PR). La validación de commits reutiliza `validarMensaje` de `scripts/commit-msg.ts` mediante un script nuevo, `scripts/validar-commits.ts`, con una función pura y un CLI delgado sobre `git log`.

**Tech Stack:** GitHub Actions (`actions/checkout@v7`, `actions/setup-node@v7`, `actions/cache@v6`, `oven-sh/setup-bun@v2`), Bun 1.4.4 (`packageManager`), Node 24.22.0, `bun test`. Sin dependencias nuevas.

**Spec:** `docs/superpowers/specs/2026-11-22-issue-10-ci-design.md`

## Global Constraints

- Sin dependencias nuevas en `package.json`; sin Python (solo Bun/Node/bash).
- Permisos del workflow: solo `contents: read`. Sin secretos reales ni `secrets.*`.
- Node exactamente `24.22.0`; Bun se obtiene de `packageManager` (no duplicar la versión en el workflow).
- Acciones con etiqueta mayor: `actions/checkout@v7`, `actions/setup-node@v7`, `actions/cache@v6`, `oven-sh/setup-bun@v2`.
- Nombres de job estables: `verificar` y `commits` (candidatos a checks requeridos).
- Los SHA del PR llegan por variables de entorno; nunca `${{ ... }}` dentro de un `run:`.
- La validación de commits usa `validarMensaje(mensaje, { ignorarComentarios: false })`; no valida el título del PR.
- Commits en Conventional Commits (el hook local ya lo exige). Prosa, comentarios y mensajes de error en español.
- **No modificar los rulesets `proteger-dev` / `proteger-main`** sin autorización explícita del responsable.
- No subir (`git push`) ni abrir PR sin confirmar con el responsable en la Task 5.
- Alcance H0: nada de despliegue, matriz de versiones, PostgreSQL en CI, E2E ni dependabot.

## Review Focus

1. **Commit inválido en medio del rango:** el CLI debe salir con 1 y nombrar el SHA corto y el motivo de cada commit inválido, no solo el primero (Task 1).
2. **Rango vacío (`base == head`):** sale con 0 y un mensaje informativo, sin error (Task 2).
3. **Argumento que no es un SHA completo (p. ej. `--all`, o texto vacío):** el CLI sale con 2 sin invocar `git log` con él (evita inyección de opciones) (Task 2).
4. **Commit base ausente (clon superficial o SHA inexistente):** `git log` falla; el CLI debe salir con 2 y un mensaje claro, nunca con 0 (Task 2).
5. **Cabecera que empieza por `#` y mensajes con CRLF:** en commits ya guardados `#` no es comentario, así que debe rechazarse; CRLF no debe producir falsos negativos (Task 1).

### Task 1: Función pura `validarCommits`

**Files:**
- Create: `scripts/validar-commits.ts`
- Test: `tests/unit/validar-commits.test.ts`

**Interfaces:**
- Consumes: `validarMensaje(mensaje: string, opciones?: { ignorarComentarios?: boolean }): string | null` de `scripts/commit-msg.ts`.
- Produces (usado por Task 2):
  - `export type CommitRango = { sha: string; mensaje: string }`
  - `export function analizarLog(salida: string): CommitRango[]` — parsea la salida de `git log --format=%H%x00%B%x1e`: registros separados por `\x1e`, SHA y mensaje separados por `\x00`; ignora registros vacíos (incluido el salto de línea que `git log` deja tras `\x1e`).
  - `export function validarCommits(commits: CommitRango[]): string[]` — un elemento por commit inválido, con el formato `<sha7>: <primera línea del error de validarMensaje>`; lista vacía si todos son válidos.

- [ ] **Step 1: Escribir las pruebas que fallan** en `tests/unit/validar-commits.test.ts` (patrón de `tests/unit/commit-msg.test.ts`):
  - `analizarLog` con dos commits (`"<40 hex>\x00feat: a\n\n\x1e\n<40 hex>\x00fix: b\n\x1e\n"`) devuelve 2 elementos con `sha` y `mensaje` correctos; con `""` devuelve `[]`.
  - `validarCommits([{ sha, mensaje: "feat(h0): ok" }])` → `[]`.
  - Review Focus 1: tres commits (válido, inválido `"arreglos varios"`, inválido `"Feat: x"`) → 2 errores, cada uno empieza por su `sha.slice(0, 7) + ": "`.
  - Review Focus 5: `"# 12 arreglar"` → 1 error (no es comentario); `"feat: con crlf\r\n\r\ncuerpo\r\n"` → `[]`.
  - Un merge `"Merge pull request #1 from a/b"` → `[]`.
- [ ] **Step 2: Ejecutar y ver el fallo.** Run: `bun test ./tests/unit/validar-commits.test.ts`. Expected: FAIL (módulo inexistente).
- [ ] **Step 3: Implementar `analizarLog` y `validarCommits`** en `scripts/validar-commits.ts` con las firmas de arriba. `validarCommits` llama a `validarMensaje(c.mensaje, { ignorarComentarios: false })` y toma la primera línea del error devuelto. Cabecera de archivo en español como la de `commit-msg.ts` (uso, y que lo consume la CI). Sin CLI todavía.
- [ ] **Step 4: Ejecutar y ver que pasa.** Run: `bun test ./tests/unit/validar-commits.test.ts`. Expected: PASS.

### Task 3: Workflow `ci.yml`

**Files:**
- Create: `.github/workflows/ci.yml`

**Interfaces:**
- Consumes: scripts `format:check`, `lint`, `check`, `test`, `build` de `package.json`; `scripts/validar-commits.ts` (Task 2).
- Produces: checks de GitHub `verificar` y `commits`.

- [ ] **Step 1: Crear `.github/workflows/ci.yml`** con exactamente esta estructura (valores fijados por el spec; el cuerpo de los pasos es copia exacta):

```yaml
name: CI

on:
  pull_request:
    branches: [dev, main]
  push:
    branches: [dev, main]

permissions:
  contents: read

concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

jobs:
  verificar:
    name: verificar
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v7
      - uses: oven-sh/setup-bun@v2 # versión de Bun: campo packageManager de package.json
      - uses: actions/setup-node@v7
        with:
          node-version: 24.22.0
      - uses: actions/cache@v6
        with:
          path: ~/.bun/install/cache
          key: bun-${{ runner.os }}-${{ hashFiles('bun.lock') }}
          restore-keys: bun-${{ runner.os }}-
      - run: bun install --frozen-lockfile
      - run: bun run format:check
      - run: bun run lint
      - run: bun run check
      - run: bun run test
      - name: build
        run: bun run build
        env:
          NODE_ENV: production
          DATABASE_URL: postgresql://traveltech:ci-sin-secreto@localhost:5432/traveltech_private
          DEMO_DATABASE_URL: postgresql://traveltech:ci-sin-secreto@localhost:5432/traveltech_demo
          AUTH_SECRET: ci-auth-secret-ficticio-solo-para-ci-0123456789
          APP_ORIGIN: http://localhost:4321
          PRIVATE_STORAGE_DIR: ./storage/private
          DEMO_STORAGE_DIR: ./storage/demo
          AGENCY_TIMEZONE: America/Mexico_City

  commits:
    name: commits
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - uses: oven-sh/setup-bun@v2
      - name: Validar los commits del PR
        run: bun scripts/validar-commits.ts "$BASE_SHA" "$HEAD_SHA"
        env:
          BASE_SHA: ${{ github.event.pull_request.base.sha }}
          HEAD_SHA: ${{ github.event.pull_request.head.sha }}
```

## Criterios de aceptación (del spec)
- `verificar` y `commits` pasan en un PR hacia `dev` (aceptación inicial).
- Instalación reproducible demostrada: `bun install --frozen-lockfile` sin modificar `bun.lock`, en clon limpio y en GitHub.
- Sin secretos reales en el repositorio ni en el workflow.
- ADR-022, guía de desarrollo y `docs/00-estado.md` actualizados, con limitaciones registradas.
- Pendiente declarado: validación en `main` tras `dev → main` y checks requeridos en rulesets (solo con su aprobación).
